{{ notes.section('What you are seeing', [ 'The clock, the pulse bar and your clicks all live on the main thread — the one thread the browser has for running your JavaScript and painting the page and handling input.', 'Run on the main thread: the loop hogs that thread. The clock stops, the bar freezes, clicks are queued and all fire at once when it finishes. The browser may show a "page unresponsive" dialog. Note that the progress bar cannot update either — there is no moment for it to paint.', 'Run in a Web Worker: identical loop, different thread. The clock ticks, clicks register immediately, and progress messages arrive via postMessage and paint as they come.', 'The total time is roughly the same either way. Workers do not make work faster; they stop it from blocking.' ], 'accent') }} {{ notes.section('How workers work', [ 'A worker is a separate JavaScript thread with its own global scope. It has no document, no window, no DOM — only self, timers, fetch, IndexedDB and message passing.', 'Communication is postMessage both ways. Data is structured-cloned (copied) unless you transfer it: postMessage(buffer, [buffer]) hands over an ArrayBuffer with no copy, leaving the sender with an empty one.', 'SharedArrayBuffer + Atomics allow true shared memory between threads, but require the page to opt into cross-origin isolation headers.', 'Worker code must come from a separate URL (here /static/js/lab_worker.js) or a Blob URL; module workers (type: "module") can import.' ]) }} {{ notes.section('Gotchas', [ 'Spawning a worker costs a few milliseconds and some memory. Sending a 50 MB image to a worker and back is two 50 MB copies — transfer the buffer instead.', 'Workers cannot touch the DOM, so pattern is: compute in the worker, post a compact result, render on the main thread.
