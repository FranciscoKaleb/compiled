{{ notes.section('What you are seeing', [ 'Load the first page, press Someone else inserts a row, then Next page. With offset, the new row at the top pushed everything down by one, so OFFSET 10 now starts at what used to be item 10 — which you already saw. It is highlighted as a duplicate. Delete a row instead and you would skip one, silently.', 'With cursor, the next page asks for "rows older than the last one I saw" — WHERE (created_at, id) < (?, ?). New rows at the top cannot shift that boundary. No duplicates, no gaps.', 'The cursor is just the sort key of the last row (created_at|id). It is opaque to the client and meaningful only to the server. The id tiebreaker matters: two rows with the same timestamp would otherwise be ambiguous.', 'Look at the SQL: offset pagination still reads and discards the skipped rows. Page 200 of an offset list makes the database read 2,000 rows to return 10.' ], 'accent') }} {{ notes.section('Choosing', [ 'Cursor (a.k.a. keyset or seek pagination) for anything that changes while people read it — feeds, activity logs, message lists, "load more" buttons, APIs. Constant cost per page regardless of depth, because it uses the index.', 'Offset when users need to jump to an arbitrary page number or see a page count, and the data is mostly static — search results, admin tables, reports. Simple, and every framework has it built in.', 'The two can combine: offset within a snapshot (a fixed as_of timestamp), or cursor plus an approximate total count for the UI.', 'Cursor pagination requires a stable, unique sort order. Sorting by a non-unique column alone (ORDER BY created_at) is where it breaks — always add the primary key as the final tiebreaker.' ]) }} {{ notes.section('Gotchas', [ 'Offset skips are worse than duplicates: a duplicate is visible, a skipped item just never appears.
