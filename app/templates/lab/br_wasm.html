            'Both sides compute the same escape-time fractal: for each pixel, iterate z = z² + c until it escapes or hits the limit. It is all floating-point multiply-add in tight nested loops — the kind of code compilers love.',

        {{ notes.section('What WebAssembly actually is', [
            'A compact binary instruction format for a stack machine, with a small set of types (i32, i64, f32, f64) and structured control flow. Browsers compile it to native code before running it. The page fetched a .wasm and called WebAssembly.instantiate.',
            'It is a compile target: C, C++, Rust, Go, Zig and others produce it. Nobody writes it by hand except for demos like this one — read scripts/build_wasm.py to see how little there is to it.',
            'It has no access to the DOM, the network or anything else. Everything goes through imports and exports across the JS boundary. That sandbox is why browsers were willing to ship it.',
            'Predictable performance is the real selling point: no garbage collector pauses, no deoptimisation cliffs, the same speed on the first call as on the thousandth.'
        ]) }}
        {{ notes.section('When it helps — and when it does not', [
            'Helps: numeric kernels (image and audio processing, physics, compression, crypto), porting existing native libraries (ffmpeg, SQLite, image codecs, games), and code that must not have GC pauses.',
            'Does not help: DOM-heavy UI code, string manipulation, anything that spends its time calling browser APIs. Each JS↔Wasm call costs a little, and copying strings across the boundary costs more.',
            'Modern JITs make well-typed JavaScript very fast. Measure before rewriting; a typed-array loop in JS is often within 20% of Wasm.',
            'Debugging and bundling are harder, binaries need to be fetched and compiled (cache them), and threads need the cross-origin isolation headers.'
